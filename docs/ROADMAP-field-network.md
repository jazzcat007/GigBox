# Roadmap item: the Pi's own WiFi network, for use away from home

**Status (2026-11-27): planned, nothing built.** Every claim below is **UNVERIFIED** unless it says
VERIFIED. Nothing here has been run on the Pi except the read-only checks listed under "What the Pi
is today".

## The idea

At home the Pi joins the house WiFi, and a phone on the same WiFi opens the touch UI (port 80, the
same screen as the HDMI panel). At a gig, a rehearsal room or a friend's place there is no known
WiFi, so the phone cannot reach the Pi. The fix: **the Pi makes its own WiFi network** (an access
point). A phone joins it, opens `http://<the Pi>/`, and controls routing, the clock, layouts and
panic exactly as at home. No router, no internet, no cable.

This is "carry the rig somewhere and control it from a phone". It is **not** reaching the Pi over
the internet from anywhere. That stays out: the hub roadmap says nothing is internet-facing by
default, and this item keeps it that way. (If remote access over the internet is wanted later it
is a separate item with its own threat model.)

## Requirements from the owner (2026-11-27)

1. **Configurable.** Mode, band, channel, SSID, passphrase, which WiFi adapter plays which role,
   and the fallback timings are settings, not constants (the Settings page and the config file,
   as everything else; see "Settings").
2. **A second USB WiFi adapter is supported.** With two adapters the Pi can be on the house WiFi
   and run its own network at the same time.
3. **Automatic fallback to the hotspot, on by default and switchable.** When the Pi cannot
   connect to any network in its list of saved, auto-connect networks, it raises its own network
   by itself.

## What the Pi is today (read-only checks, 2026-11-27)

- **VERIFIED.** Raspberry Pi 3 Model B+, Debian 13 (trixie), NetworkManager 1.52.1.
- **VERIFIED.** `wlan0` is a client of the home WiFi; `eth0` has no cable. The two profiles are
  generated by netplan (`netplan-wlan0-...`); the user is in the `netdev` group.
- **VERIFIED.** `nmcli device show wlan0` reports `WIFI-PROPERTIES.AP: yes`, with 2.4 GHz and 5 GHz
  both yes (the BCM43455 on the 3B+). So the hardware and NetworkManager can run an access point.
- **VERIFIED.** `iw phy` on the onboard radio lists the interface combination
  `{ managed } <= 1, { AP } <= 1 ... #channels <= 1`: it can be a client and an access point at
  once, but both on the same channel. That is why one adapter cannot serve the house WiFi and its
  own network independently, and why a second adapter is worth having.
- **VERIFIED.** The headless server (`fm1-web-headless`, a system unit running as the user) already
  listens on `0.0.0.0:80` and already requires the write token for clients that are not on the Pi.
  An access point therefore needs no new server code to be reachable.
- **VERIFIED.** There is no real-time clock and no `fake-hwclock`; time comes from NTP while the
  home network is up. Away from home it would not (see "Clock" below).
- `avahi-daemon` is running, so `fm-pi.local` resolves on the home network. `hostapd` and
  `dnsmasq` are not installed and are **not needed**: NetworkManager's own hotspot mode starts
  both internally.

## Design

### Modes

| Mode | What the Pi does | Use |
|---|---|---|
| **Auto** (the default) | joins a saved network; if none works, raises its own (see "Fallback") | normal |
| **Home** | joins saved networks only, never raises its own | a rig that must never broadcast |
| **Field** | always runs its own network, never joins one | a gig, when the house WiFi should be ignored |

With **one adapter** these are exclusive: the radio is either a client or an access point.
With **two adapters** a fourth case opens up, *Both*: one adapter is the client and the other
is the hotspot, at the same time (see "Two adapters"). It is a setting on top of the mode, not a
fourth mode: Auto or Field with "keep the hotspot up while connected" turned on.

### Fallback

"The list" is the Pi's own saved WiFi profiles that have auto-connect on (today `HomeWiFi`;
the hotspot profile is never in it). Nothing about the list changes: networks are added and
removed the way they are now. **Adding a network with a password through this UI is out of scope**
for the first build; it would put WiFi secrets through the web server.

- **On boot, or when the link is lost:** if no saved network connects within `fallback_after`
  seconds (default 60), the hotspot comes up. "Lost" means connected earlier and the link has been
  down for `fallback_after`. Both are individually switchable (`fallback_at_boot`,
  `fallback_on_loss`); mid-session fallback matters at a gig, where the venue WiFi can disappear.
- **Coming back:** while the hotspot is up because of a fallback, the Pi scans for saved networks
  every `retry_home_every` minutes (default 5; 0 means never). It switches back **only when no
  phone is joined to the hotspot** (the client count is readable from the access point), so it
  never kicks someone who is using it. A setting can turn that guard off.
- **Never loop.** After a switch back that fails, the next attempt waits twice as long, up to
  an hour. A wrong password or a flaky venue network must not make the Pi flap.
- **Two adapters:** the fallback is not needed to keep a phone connected, because the hotspot
  can simply stay up (below); a failed home link then only affects the Pi's internet.

Who decides. Two ways to build it; **UNVERIFIED** which behaves better, so step 3 below measures:

1. NetworkManager's own: a hotspot profile with a lower auto-connect priority is used only when
   no higher one can connect. Free and robust, but it has no "only when nobody is joined" guard,
   no back-off, and no clean way to read why it chose what it chose.
2. A small supervisor in `fm1-switch` (its own user service) that watches the connection state
   and calls the fixed-verb helper. More code, all the rules above, and testable with a fake
   `nmcli`. **Chosen for the first build, as the only decider:** the hotspot profile is made with
   auto-connect off, so NetworkManager never raises it on its own and the two cannot race.
   systemd restarts the supervisor if it dies.

### Two adapters

A USB WiFi adapter is a second `wlan` device. Because they are different radios there is no
channel coupling, so the house WiFi and the Pi's own network can run together.

- **Roles by identity, not by name.** `wlan0` and `wlan1` can swap on replug, the same trap as ALSA
  card numbers. A role is bound to the adapter's **MAC address** (or USB port path), the way units
  are bound to the registry id. Default: the hotspot goes on the best adapter that can do access
  point mode (a USB one with a proper antenna if it can, else the onboard radio), the client on
  the other. Both overridable (`client_adapter`, `hotspot_adapter`; `auto` or a MAC). The roles
  follow capability, so a second adapter that cannot be an access point is still useful: it
  becomes the client and the onboard radio is the hotspot.
- **The adapter must support AP mode.** Checked at runtime (`nmcli device show`, the
  `WIFI-PROPERTIES.AP` line, as verified for the onboard chip). Many cheap adapters and their
  drivers do not; a chipset that does is a purchase decision, so **the doc lists a known-good
  adapter only after one is tested on the bench.** UNVERIFIED which.
- **Hotplug.** Adapter unplugged: the hotspot falls back to the single-adapter rules above. Plugged
  in: it is picked up on the next scan, no restart.
- **Power.** One more device on a Pi that already shows under-voltage and temperature limits. A
  powered USB hub is already a recommendation of the hub roadmap; it applies here too.
- **No forwarding.** NetworkManager's shared mode **masquerades** hotspot traffic out through
  whichever interface has the default route. With two adapters, or with `eth0` cabled, that would
  let a phone on the Pi's network reach the house LAN and the internet through the Pi. Unwanted:
  it is a rig controller, not a router. **Requirement:** forwarding between the hotspot and any
  other interface is off by default (a firewall rule, UNVERIFIED how best to do it under
  NetworkManager 1.52), with an explicit "share the Pi's connection" setting, off, for anyone who
  wants it.

### Settings

All in the config schema (`config.py`) so they appear on the Settings page with no UI change:

| Key | Default | Meaning |
|---|---|---|
| `net_mode` | `auto` | `auto`, `home` or `field` |
| `net_fallback_at_boot` | on | raise the hotspot when no saved network connects at boot |
| `net_fallback_on_loss` | on | raise it when a connected link is lost |
| `net_fallback_after` | 60 s | how long to wait before giving up on the saved networks |
| `net_retry_home_every` | 5 min | scan for saved networks while in fallback (0 = never) |
| `net_retry_only_when_empty` | on | switch back only when no phone is joined |
| `net_hotspot_always_on` | off | keep the hotspot up while connected (needs a second adapter) |
| `net_client_adapter`, `net_hotspot_adapter` | `auto` | which adapter, `auto` or a MAC |
| `net_ssid` | `FM-Pi-<id>` | network name |
| `net_band`, `net_channel` | 2.4 GHz, 6 | 2.4 or 5 GHz; a fixed channel, never "auto" |
| `net_share_connection` | off | forward the hotspot to the Pi's other connections |

The passphrase is **not** a plain setting. It is generated on first use and kept in a 0600 file
like the write token; the owner can set their own (8-63 characters) from the panel or the
expert page through a write-only field that never shows it back. The config schema has no
"yes or no" or "pick one" setting kind today, only path, int, float, text and url, so this
item adds two (`bool`, `choice`) and the Settings page renders them. Defaults are a proposal:
2.4 GHz channel 6 is what the fm1-radio units can join and has the longest range; a venue full
of 2.4 GHz traffic is the reason 5 GHz is one setting away.

### The network

- A separate NetworkManager profile (`fm1-hotspot`), created by `nmcli`, **never by editing the
  netplan files**, so `netplan apply` cannot remove it. (**UNVERIFIED** that it survives one.)
- Address: NetworkManager's shared mode gives the Pi `10.42.0.1` and hands phones addresses by DHCP
  (default `10.42.0.0/24`). Fixed and predictable, which matters because `fm-pi.local` is **not**
  reliable on every phone: iOS and macOS resolve it, Android and some Windows setups do not. The
  touch UI therefore shows the plain address, and a QR code (below).
- SSID `FM-Pi` plus the Pi's short id, so two rigs in one room do not collide.
- **Security.** WPA2-PSK at least (WPA3 if the chip's firmware does it; UNVERIFIED), a generated
  passphrase kept in a 0600 file like the write token and **not** shown on the Settings page.
  The write token stays on: the passphrase says who may join, the token says who may change
  anything. Throttling on the server already exists. Client isolation (phone cannot see phone)
  is wanted; NetworkManager 1.52 may expose it as `802-11-wireless.ap-isolation`. UNVERIFIED.
- Band and channel are settings (see "Settings"). 5 GHz is quieter at a venue, but **fm1-radio
  units join 2.4 GHz only** (see the fm1-radio notes), so a rig that wants its units on the Pi's
  network needs 2.4 GHz. A fixed channel, never "auto".

### Switching, without locking yourself out

Switching Home to Field drops whatever phone is controlling the Pi over the house WiFi. So:

- The switch is explicit, confirmed, and shows what will happen ("this phone will disconnect;
  join FM-Pi, password on the panel").
- **Dead man's switch:** after a switch the Pi waits 60 s for a request from the new network. If
  none comes, it goes back to the previous mode. A wrong passphrase or a phone that never joined
  must not leave the Pi unreachable.
- The touch panel (HDMI screen) can always switch, since it is on the Pi itself.
- Changing network config needs rights. The user is in `netdev`, which normally lets `nmcli` manage
  WiFi without sudo (**UNVERIFIED**, and `sudo` on the Pi needs a password, so it cannot be a
  requirement). The web server must **not** pass arbitrary text to `nmcli`: a small helper with a
  fixed set of verbs (`status`, `home`, `field`, `auto`) and nothing else.

### On the panel and the phone

- A NETWORK screen: mode, SSID, address, how many phones are joined, and a **QR code** in the
  standard WiFi format (`WIFI:T:WPA;S:<ssid>;P:<passphrase>;;`) so a phone joins with one scan, then
  a second QR for `http://10.42.0.1/`. The passphrase is on the physical panel only, never on the
  phone UI. Whether the write token is also shown there is a decision: anyone who can see the
  panel is in the room, but the token is a second factor, so it appears only behind a confirm.
- The same status is in the expert page's Settings (mode, band, channel, SSID).

### Clock

With no internet and no RTC the Pi boots with the time it last had, or 1970. It matters here:

- The flash log, backup folder names and the sets file carry dates; wrong ones make an audit
  trail misleading.
- The router's flash holds expire on wall-clock time. A jump when time is corrected could make a
  hold expire early or late. (Holds always expire, so a unit is never silenced for ever, but the
  gap between "set" and "expires" can be wrong.) To check in the code.
- Fix, cheapest first: install `fake-hwclock` (restores the last saved time at boot, so time never
  goes backwards); let the phone set the time from the UI when it connects (the browser knows the
  time); a DS3231 RTC module if the rig is used offline for long.

### Without internet

**Built (2026-11-28).** Anything that needs the hub checks a cached connectivity test first (no default route, or
the hub unreachable within a few seconds, means offline), so it fails in a moment with an explanation rather than
waiting out the 60 s catalogue or 180 s download timeout. Offline: the saved catalogue is served and marked
offline with its age, downloads are refused with a message that names what still works and the way around it
(`fm1-switch import` from a USB stick), the admin page and the touch screen show it and grey the buttons, and the
CLI prints it and exits with an error. Guide: [GUIDE-wifi-hotspot.md](GUIDE-wifi-hotspot.md). The clock problem
below is still open.

### Hardware

- The 3B+ radio supports AP mode, but it is a small radio: expect a few phones near the Pi, not a
  room. A USB WiFi adapter is the upgrade and is supported (see "Two adapters"): better range, and home
  WiFi and the Pi's own network together.
- Power: the Pi has shown under-voltage and soft temperature limits since boot (`throttled`
  is `0x80000` today: only the temperature limit has been hit this boot). An access point is
  extra load on a Pi that already feeds four units and an Oxi One. **Measure before relying on
  it**, as the hub roadmap says for the units.
- A phone that joins a WiFi with no internet may drop back to mobile data, or warn about it.
  Say "keep this connection" in the join instructions.

### Not recommended

- **Home and Field at the same time on one radio.** The chip can run a station and an AP together
  only on the same channel, so the Pi's network would have to follow whatever channel the house
  router uses. Fragile. With one adapter use modes; with two, use the second adapter.
- Captive-portal tricks. Not needed: the QR code and a fixed address are simpler.
- Bridging the Pi's WiFi into the house network. It is a rig controller, not a router.

## Possible extras (only if wanted)

- **Ethernet, shared:** a laptop on a cable to `eth0` gets an address from the Pi (NetworkManager
  shared mode again). No WiFi needed. `eth0` is on the same hub as the units, which share a
  small USB bus; MIDI and the web UI are tiny, so this is fine.
- **fm1-radio units join the Pi's network.** Needs the AP on 2.4 GHz. UNVERIFIED whether the
  radio firmware's WiFi join works against a NetworkManager hotspot (WPA2-PSK is the likely case).
- **Network MIDI (RTP-MIDI) over the Pi's network**, so a phone or laptop plays the units, as in
  the hub roadmap's Connectivity list. Needs `rtpmidid`, which is not installed. Over WiFi, jitter
  is a real concern for playing; fine for control.

## Built so far (2026-11-27): the fallback, one adapter

Not deployed to run on the Pi yet. Written and tested on the Mac with a fake `nmcli`; no network
was touched. Scope: the onboard radio only. The second adapter, the panel NETWORK screen, QR codes
and the clock are later steps.

- `fm1_switch/netctl.py`: the only code that runs `nmcli`, as a fixed set of operations (read the
  adapter, list saved networks, make or update the `fm1-hotspot` profile with auto-connect off,
  hotspot up and down, join a saved network, count joined phones with `iw`, the passphrase file
  at mode 0600, the text for a join QR code). It never creates, changes or deletes a saved network.
- `fm1_switch/netwatch.py`: the rules as a state machine that touches nothing (boot rule, link-lost
  rule, retry only when nobody is joined, back-off to an hour, `home` and `field` modes) and the loop
  that observes, acts and writes `~/fm1-net-status.json`. A failing `nmcli` is logged and the loop goes
  on.
- Settings page: a new **WiFi and hotspot** group (mode, the two fallback switches, wait before
  giving up, retry interval, the only-when-empty guard, hotspot name, band, channel, adapter) and two
  new setting kinds, yes/no and pick-one.
- CLI: `fm1-switch net status | setup | passphrase [NEW] | watch | up --yes [--for N] | down`. `up`
  is a timed manual test: it raises the hotspot, waits, then puts the saved networks back by itself.
- `systemd/fm1-net.service` (not installed) and `polkit/50-fm1-wifi.rules` (not installed).
- 42 new tests. All suites pass.

## Acceptance (for the first build)

- Power the Pi somewhere with no known WiFi: within about `fallback_after` plus a few seconds a
  network named `FM-Pi...` appears, a phone joins by QR, and `http://10.42.0.1/` shows the same
  touch UI as the HDMI panel.
- With the fallback switched off, the same Pi stays quiet and keeps looking for its saved networks.
- Home WiFi lost mid-session: the hotspot appears; home WiFi back and nobody joined: the Pi returns;
  somebody joined: it does not.
- With a second adapter: house WiFi and the Pi's network are up together, a phone on the Pi's
  network cannot reach the house LAN, and unplugging the adapter leaves the Pi reachable.
- Routing, the clock, layouts and panic work from that phone. A write without the token is
  refused.
- Switching modes never leaves the Pi unreachable (the dead-man timer is tested by joining with
  the wrong password).
- A flash, a backup and the soft key are unaffected while a phone is connected.
- The Pi's clock is sensible after a power cycle with no internet.
- Nothing is reachable from outside the Pi's own network.

## Decided, and still open

Decided by the owner (2026-11-27): everything above is configurable, a second USB adapter is
supported, and the fallback is on by default and can be switched off. The passphrase is generated
by default and can be set by the owner. **No internet access to the Pi is wanted**: the only way in
is the house WiFi or the Pi's own network, and nothing is exposed beyond them. That closes the
earlier question; remote access over the internet is out of scope for this item and needs no work.

Still open:

1. Which USB adapter? **Tried 2026-11-27: the Linksys WUSB6100M (USB 13b1:0042) is not usable.**
   It shows up on the Pi's USB hub and no driver binds. It is a Qualcomm QCA9377 part, whose only
   Linux driver is `ath10k`'s USB transport, which Linux itself labels experimental and incomplete
   ("don't expect anything to work"), and the Pi's kernel is built without `ath10k` at all
   (`# CONFIG_ATH10K is not set`). Building a driver by hand would need sudo and would still be
   that unfinished code, with no sign that access-point mode works. **Do not use it.** An adapter
   whose driver and firmware already ship with the Pi's kernel is the safer buy. Present on this Pi
   (VERIFIED): `ath9k_htc` (AR9271 chips, 2.4 GHz, the long-standing choice for hostapd),
